# 答案：时钟与时间的设计

> 对应：[time-design.md](../design/time-design.md)

## 第 1 题

**（a）** `rclcpp::Rate rate(20)` 默认用**系统时钟** 🔍，所以循环在墙钟上每 50 ms 转一圈。半速回放时，仿真时间只走一半，每圈约 25 ms 💡（推导：0.5 倍速 × 50 ms）。用 `now()` 的差值算周期的话，控制器测出来的是 40 Hz，而它的 PID 参数和前馈是按 20 Hz 调的。如果代码里又把 `dt` 写死成 0.05 s，积分和微分项都会比实际大一倍。总之，控制循环跟着墙钟走，数据跟着仿真时间走，两者对不上。

**（b）** 回放暂停时，`/clock` 停了，`now()` 不再变化 📐 🔍，但系统时钟的 `Rate` 照样每 50 ms 唤醒一次 🔍。于是每圈的 `now() - last` 都等于 0。代码里如果有 `/ dt`，会除以零或得到 inf；速度估计、加速度限制都会失灵。同时控制器还在不停地发指令，指令却是基于同一时刻的数据算出来的。💡

**（c）** 让循环跟着节点时钟走：
- 写成 `rclcpp::Rate rate(20, get_clock())` 🔍。仿真时间暂停时 `sleep()` 也会跟着停，半速时周期按仿真时间算仍是 50 ms。
- 更推荐改成 `create_timer(50ms, ...)`，由执行器调度，用的也是节点时钟 🔍，还不会阻塞线程。

另外，`dt` 要用 `now()` 的差值算，并检查 `dt <= 0` 的情况（遇到就跳过这个周期）💡。

## 第 2 题

**（a）** 第二圈开始时，`/clock` 从 60 s 跳回 0 s，就是设计文档说的"时间往回跳" 📐。之后会出现两类问题：

- **tf 外推错误**：tf2 的 `Buffer` 检测到时间往回跳时会**清空缓存** 🔍（日志 `Detected jump back in time. Clearing TF buffer.`）。在新的变换重新填满缓存之前，按新时间去查都会失败；有的节点自己也缓存了旧时间戳的数据，用它们去查同样会失败。💡
- **加速度尖峰**：速度平滑器保存的"上一次时间戳"是 60 s 左右，新时刻是 0 s 左右，算出 `dt ≈ -60 s`，或者被保护成一个极小的正数，于是加速度的计算结果是一个巨大的值。💡

**（b）** 设计文档要求提供**时间跳变回调**：时间往回跳时，先调用用户注册的回调，回调完成后才报告新时间，让用户有机会清掉状态 📐。

Rolling 里的用法是 `get_clock()->create_jump_callback(pre_cb, post_cb, threshold)` 🔍：
- 在 `post_cb` 里检查 `jump.delta`，小于 0 就重置平滑器保存的上一次时间戳和速度、清空滤波器、重新对齐轨迹的时间索引。💡
- 阈值的设法：`min_backward` 设成 -1 ns，任何往回跳都报；`min_forward` 设成 1 s 左右，只报大的向前跳变 🔍。如果 `min_forward` 设得太小，**每次 `/clock` 更新**都会触发一次回调 🔍。`on_clock_change=true` 可以顺便处理 `use_sim_time` 被切换的情况 🔍。

**（c）** steady 时钟确实不会往回跳，但它和数据不在同一个时间轴上 💡：
- 回放倍率不是 1 时，数据之间的时间间隔（看时间戳）和 steady 时钟算出的 dt 不一致。比如 2 倍速回放时，两帧数据在仿真时间里相隔 100 ms，steady 时钟上只隔了 50 ms，算出的速度会偏大一倍。
- 回放暂停时，steady 时钟照样走，下一帧到来时 dt 突然变得很大。
- 消息时间戳是 ROS 时间，steady 时间不能和它混用：比较时运行时抛 `can't compare times with different time sources` 🔍，相减时抛 `can't subtract times with different time sources` 🔍（librclcpp 里的错误字符串）。

正确的做法仍然是统一用 ROS 时间，再用跳变回调处理往回跳。设计文档对 steady 的定位是只用于硬件超时，并且要把它隔离在驱动内部 📐。
