# 答案：服务与动作的设计

> 对应：[service-action-design.md](../design/service-action-design.md)

## 第 1 题

**（a）** 同步 API 一次调用占住一个线程直到返回。想用同步 API 实现"同时等 3 个结果"，只能开 3 个线程各调一次，再用同步原语汇总；线程多、开销大，还要处理"其中一个超时了另外两个怎么办"。异步 API 发出 3 个请求立刻返回 3 个 future，一个线程用 `wait_for` 轮流等，或者注册回调，谁先回来先处理。所以异步是更底层、更灵活的原语，同步只是"发出请求 + 在 future 上阻塞"这么一层。📐 💡

**（b）** 出在"阻塞等 future"这一步：future 要靠执行器处理响应才会就绪，而你阻塞的恰恰是执行器正在用的那个线程（在订阅回调或定时器回调里 `future.wait_for`/`get()`）。执行器没法去处理响应，future 永远不会就绪，直到超时。📄 解决办法是把客户端放进另一个回调组并用多线程执行器，或者改用 `async_send_request` 的回调形式，不阻塞（见 [服务](../cards/communication/service.md)、[回调组](../cards/concurrency/callback-group.md)）。

## 第 2 题

**（a）** 拿到 `STATUS_UNKNOWN`、结果为空。动作服务端只缓存结果 `result_timeout`，Rolling 的 rcl_action 默认 10 s 🔍；20 秒后结果已经被丢弃，服务端不再认识这个目标 ID。实测：完成后 3 s 取到 SUCCEEDED，12 s 取到 UNKNOWN 🔍。（如果 20 秒内目标还在执行，就能取到，结果会在完成后返回。）

**（b）** 目标 ID 是**客户端**生成的 UUID，任务管理器在发出目标的同时就知道 ID，可以先写进数据库再等结果；重启后还能拿这个 ID 去问 `get_result`，或者去 `status` 话题里找。如果 ID 由服务端生成，崩溃发生在"响应回来之前"时，客户端根本不知道 ID。设计文档还提到另一个好处：可以把它和外部系统里已有的任务 UUID 对应起来。📐

**（c）**（💡，任选两种）

1. 服务端创建时把 `rcl_action_server_options_t::result_timeout` 调大，例如 300 s，覆盖任务管理器的最长重启时间（-1 表示永久保留，但会一直占内存）。
2. 把"结果"本身变成持久状态：导航完成后由服务端或另一个节点把结果写到一个 TransientLocal 话题或数据库里，不依赖动作的结果缓存。
3. 重启后订阅 `<动作名>/_action/status`（TransientLocal，能拿到最新一份）按目标 ID 查终态。🔍 实测：结果过期后新建的状态订阅**仍然收到 SUCCEEDED**（过期时服务端没有重新发布状态），所以至少能知道成功还是失败；但这时 `get_result` 返回 UNKNOWN，两者不一致，拿不到结果内容。另外，只要服务端之后再发布一次状态（例如来了新目标），旧目标就会从列表里消失，所以这只是"碰运气"的补救。
