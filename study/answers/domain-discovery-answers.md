# 答案：Domain ID 与发现

> 先在[卡片](../cards/middleware/domain-discovery.md)里自己写下答案再来对照。

## 题 1：3 台机器人、5 个开发者共用 Wi-Fi

一种满足要求的配置（机器人 R1–R3，开发者 D1–D5，假设 D1、D2 负责 R1，D3 负责 R2，D4、D5 负责 R3）：

| 机器 | `ROS_DOMAIN_ID` | `ROS_AUTOMATIC_DISCOVERY_RANGE` | `ROS_STATIC_PEERS` |
|---|---|---|---|
| R1 | 11 | `LOCALHOST` | 不设 |
| R2 | 12 | `LOCALHOST` | 不设 |
| R3 | 13 | `LOCALHOST` | 不设 |
| D1、D2 | 11 | `LOCALHOST` | R1 的 IP |
| D3 | 12 | `LOCALHOST` | R2 的 IP |
| D4、D5 | 13 | `LOCALHOST` | R3 的 IP |

理由：

1. **机器人内部互通、不往 Wi-Fi 上多播**：`LOCALHOST` 只在本机发现。同一台机器上 `LOCALHOST` 和任何非 `OFF` 设置都互通。
2. **笔记本只看到自己的机器人**：跨机器时，两边都不是 `SUBNET` 就需要至少一边写静态对端。只在笔记本上写机器人 IP 就够了（🔍 实测：一边写对端、另一边不写，能通），机器人不需要知道有哪些笔记本，部署简单。
3. **为什么还要分 Domain**：理论上发现范围已经隔离了；但只要有人忘了设 `LOCALHOST`（默认 `SUBNET`），他的节点就会在 Wi-Fi 上多播。不同 Domain 用不同端口，多播报文被丢在门外，多一层保险。
4. **负责同一台机器人的 D1、D2 会不会互相干扰**：它们在同一个 Domain，但两台笔记本都是 `LOCALHOST`、互相没写对端，按"跨机器两边都不是 `SUBNET` 就要靠静态对端"的规则，它们互相看不见，只各自看得到 R1。需要互通时再互相加对端。
5. 💡 Domain 号选 0–101 之间。别用 0：新同事、新设备不设变量时默认就是 0，会撞进来。

注意：改完这些变量要 `ros2 daemon stop`，否则 CLI 看到的还是旧配置。

## 题 2：Domain 0 跑了 130 个进程，Domain 1 的同事收到奇怪连接

端口公式：参与者 $p$ 在 Domain $d$ 的单播端口是 $7400 + 250d + 10 + 2p$ 和 $+11+2p$。

- Domain 0 的第 $p$ 个参与者：$7410 + 2p$、$7411 + 2p$。
- Domain 1 的多播端口是 $7400 + 250 = 7650$（和 7651），单播从 7660 开始。
- 当 $p = 120$ 时，Domain 0 这个参与者的单播端口是 $7410 + 240 = 7650$、$7651$，**正好撞上 Domain 1 的多播端口**；$p > 120$ 的继续占用 Domain 1 参与者的单播端口（$p=125$ → 7660、7661，就是 Domain 1 第一个参与者的端口）。

130 个进程意味着 $p$ 到了 129，Domain 0 的发现和数据报文落到了 Domain 1 在用的端口上，同事那边就会收到"不属于自己"的连接尝试，或者端口被占导致自己的参与者换端口、行为异常。📄 文档的说法：同一台机器同一 Domain 超过 120 个进程会溢出到其他 Domain 的端口。

解决办法：

1. **减少参与者数量**：每个进程一个参与者，和节点数无关。把仿真里的节点组合进少数几个进程（[组件与组合](../cards/concurrency/component.md)，一个容器进程装几十个组件），参与者数立刻降下来。
2. **把两个 Domain 拉开**：同事改用离 0 远的 Domain（如 50），中间隔出足够的端口；或者仿真放到单独的机器、容器（bridge 网络）里，端口空间不再共享。
3. 💡 也可以把仿真的发现范围设成 `LOCALHOST`、同事用另一台机器；但端口冲突发生在同一台机器上，只改发现范围不能解决端口重叠，根本办法还是前两条。
