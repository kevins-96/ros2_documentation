# 答案：为什么有 ROS 2、为什么建在 DDS 上

> 对应：[why-ros2-dds.md](../design/why-ros2-dds.md)

## 第 1 题

**理由（答出 3 个即可）：**

1. **去掉中心 master。** ROS 1 的发现依赖单一 master，它是单点故障，多机器人只能变通；DDS 默认分布式发现，任何两个 DDS 程序不需要中心就能通信。📐
2. **新场景要的是"可调的可靠性"，不只是"多一个 UDP"。** 有损 Wi-Fi、实时控制需要按话题选择"重传直到送达"还是"丢了就丢了、只要最新"。DDS 跑在 UDP 上、自己实现可靠性，所以能用 QoS 精细控制；在 TCPROS 上加 UDP 只是多一种传输，没有这套语义。📐
3. **有成文规范、可审计。** DDS 有 API 规范和 DDSI-RTPS 线上协议规范，多家厂商实现；产品和关键任务用户需要能认证、审计的东西，而 ROS 1 只有 wiki 和参考实现。📐
4. **自己拼（ZeroMQ + Protobuf + zeroconf）的工作量被低估了。** 原型发现没有能独立使用的现成发现系统；发现与传输的衔接、类型安全、进程内传指针都要写胶水代码；最后还要补一份规范，工作量几乎等于再实现一遍。📐
5. **嵌入式和实时。** 有几十到几百 KB 的嵌入式 DDS 实现，几家实现几乎无外部依赖，打包简单。📐

**代价（答出 1 个）：** DDS 的 API 和配置很复杂，ROS 必须把它藏起来；社区文化不同（问题主要靠厂商回答，当时也没有现代包管理器的包）；部分实现是商业许可；采用端到端中间件就要接受它的设计，不合适的地方只能绕。📐 💡 实际中最常遇到的是第一条：发现、共享内存、XML 配置出问题时要懂 DDS 才能排查（见 [DDS 调优](../cards/middleware/dds-tuning.md)）。

## 第 2 题

**（a）** 推理是"相对成本"：每次发送跨进程都必须序列化，而逐字段拷贝的开销比序列化小一个数量级以上（2014 年测过的所有序列化库都如此，只有本身不需要序列化步骤的 Cap'n Proto 例外）。所以拷贝不是瓶颈；如果一个场景连这次拷贝都承受不了，那它也承受不了序列化，根本就不该走网络/跨进程这条路。📐

**（b）** 不做了。Rolling 的 `rosidl_typesupport_fastrtps_cpp` 生成的是 `cdr_serialize(const std_msgs::msg::String & ros_message, eprosima::fastcdr::Cdr &)`，直接从 ROS 的 C++ 结构体序列化成 CDR，中间没有 DDS 生成的类型 🔍。线上的类型名仍是 `std_msgs::msg::dds_::String_`，这是命名约定留下的痕迹。

**（c）** 按这条推理，瓶颈在序列化 + 传输本身，所以方向是**避免序列化**：把生产者和消费者放进同一进程用进程内通信传指针（`unique_ptr` 发布可做到零拷贝），或者用借用消息（loaned message）配合共享内存（只对定长/平铺类型有效）。见 [进程内通信与零拷贝](../cards/concurrency/intra-process.md)。🔍 第 4 批实测过：跨进程传 1 MB 以上的点云在 SensorDataQoS 下几乎全丢，而进程内通信没有这个问题（那里的主因是大消息分片后在 BestEffort 下容易丢，不只是序列化开销，但结论相同：大数据别走跨进程）。
